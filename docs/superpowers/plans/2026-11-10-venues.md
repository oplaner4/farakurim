# Venues, Step 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The parish's own buildings (2 churches, the fara, 6 chapels) are written down once, in a venue list, and the
services, Kontakty, the Betlémy page and the Bohoslužby calendar read their address and map link from it.

**Architecture:** A new content file `src/content/venues.ts` (type in `src/content/types/venues.ts`) holds one `Venue`
per building, keyed by a `VenueId`. The places of the services, the church cards and chapels of Kontakty, the office
and the nativity seasons refer to a `VenueId` instead of carrying `address`, `mapQuery` and `mapUrl` themselves. One
helper, `venueMapHref()` in `src/lib/shared/links.ts`, builds every map link from a venue.

**Tech Stack:** TypeScript, Next.js 16 (static export), Vitest (`--project` site and scripts).

**Spec:** this plan's "Design" section (agreed in conversation on 2026-11-10; no separate spec file). Step 2 (events
get a `venue`, the event skills, geocoding with the Mapy.com API) is a later plan and out of scope here.

- **The calendar addresses do not change.** `Place.address` today is the Bohoslužby calendar's `location`, and
  `scripts/lib/calendar/services-plan.ts:85` matches the existing Google events by it. The three church addresses move
  into the venues character for character, Jinačovice's (the village's address) included.
- **Jinačovice (decision):** `places.jinacovice` refers to `jinacovice-kaple`. Its Pořad bohoslužeb map link changes
  from the search "Jinačovice" to the chapel; its calendar location stays the village address above.
- **What stays service- or page-specific:** `Place.name`, `church`, `churchShort`, `color`, `locative`, `byAgreement`
  stay in `places`; `ParishChurch.building`, `note`, `color` in `parishChurches`; `contacts.street`, `postalCode`,
  `town`, `mapEmbed` in `site.ts` (8 components and the structured data use the split form); `NativityPlace` stays.
- **The map link:** `mapUrl`, else a Mapy.cz search of `mapQuery`, else of `address`, else of `"<name> <village>"`.
  The pages render the same links as today, except Jinačovice's on Pořad bohoslužeb.
- **No positions yet:** coordinates and Mapy place ids come with step 2 (the `.ics` `GEO`, the structured data).

## Global Constraints

- Code, comments, docs and commit messages in English; venue names, addresses and queries in Czech, as above.
- `src/lib` imports content types only, never content data (`.claude/rules/structure.md`); imports `./x` or `@/…`.
- Commits: Conventional Commits through the `commit` skill, scope `content` or `lib`; never `--no-verify`.
- Done means the full check `pnpm format && pnpm test && pnpm lint && pnpm exec tsc --noEmit && pnpm build` and the
  browser check of `docs/conventions.md` (Kontakty, Pořad bohoslužeb, Betlémy at 390/834/1440 px, both themes).
- Never run `pnpm calendar-sync --apply`; the preview (`pnpm calendar-sync`, no `--apply`) is allowed.

## Review Focus

- **Calendar churn:** a changed address string makes the next sync rewrite every upcoming service's location → the
  pinned-address test in Task 2.
- **Office drift:** the fara's venue address and `contacts.street`/`postalCode`/`town` disagree after a later edit →
  the consistency test in Task 3.
- **Lost map override:** the Česká chapel's link falls back to the search that finds the wrong place → the
  `venueMapHref` order test in Task 1 and the Česká assertion in Task 3.
- **A chapel without a catalogue link** renders a broken `href` on Kontakty → the catalogue test in Task 3.
- **A stale reference:** a place, church, chapel or season names a venue that is not in the list → `VenueId` typing
  plus the "every referenced venue exists" test in Task 1.
